# Семинар 10. Платформенные потоки и Java Memory Model

## План семинара

| # | Этап | Время |
|---|---|---:|
| 1 | Жизненный цикл потока: состояния Java и ОС | ~15 мин |
| 2 | Создание и запуск потоков, Thread API | ~10 мин |
| 3 | Исключения и прерывание работы потока | ~20 мин |
| 4 | Согласование работы потоков — опциональный обзор | 0–5 мин |
| 5 | Java Memory Model: предпосылки и основные гарантии | ~25 мин |
| 6 | JMH и jcstress, дополнительные эксперименты — опционально | 0–10 мин |
| 7 | Постановка задачи и демонстрация реализации подписок | ~20–35 мин |

Основной сценарий рассчитан на **90 минут**, расширенный — до **120 минут**. Дополнительное
время отдаём обзору согласования потоков, экспериментам и написанию отдельных методов
практической части. Разбор CAS и стека Трайбера опционален и входит во время финальной практики.

Сначала проходим теорию с независимыми демо, затем ставим прикладную задачу и показываем,
как изученные механизмы работают вместе. Семинарист либо разбирает готовое решение,
либо пишет его отдельные части на подготовленном каркасе. Не нужно писать весь сервис с нуля.

### Этап 1. Жизненный цикл потока: состояния Java и ОС (~15 мин)

После плана занятия переходим к потокам. Напоминаем модель 1:1 для платформенных потоков:
когда и на каком ядре исполняется поток, определяет планировщик ОС. Виртуальные потоки
упоминаем как другую модель, которую подробно разберём на семинаре 12.

По схеме разбираем шесть состояний Java и причины переходов. Запускаем `ThreadStatesDemo`,
при необходимости снимаем дамп через `jcmd <pid> Thread.print`. Акцент — на различии описаний
Java и ОС: RUNNABLE объединяет готовность и исполнение, а также может наблюдаться при native-ожидании;
BLOCKED означает ожидание монитора, а не любую блокирующую операцию.

Спрашиваем группу, какое состояние будет у потока, ожидающего сетевой ответ. Связываем
обсуждение с пройденной темой I/O: RUNNABLE в дампе не доказывает потребление CPU.
Кратко напоминаем daemon-потоки, назначение yield и park/unpark. Если нужен пример,
показываем `ParkingDemo`: один permit на поток и повторная проверка условия после park.

### Этап 2. Создание и запуск потоков, Thread API (~10 мин)

Кратко повторяем создание Thread через конструктор и builder, передачу Runnable.
В `ThreadApiDemo` показываем разницу между run и start, запрет повторного start и ожидание
завершения через join. API уже знаком группе, поэтому основное внимание уделяем поведению,
а не перечислению методов. Код подписок пока не открываем.

### Этап 3. Исключения и прерывание работы потока (~20 мин)

В `UncaughtExceptionDemo` восстанавливаем последовательность: раскрутка стека, finally,
обработчик необработанного исключения, завершение потока. Показываем индивидуальный handler
и делегирование через ThreadGroup к default handler. Handler не возвращает выполнение
к месту ошибки, а join не перебрасывает исключение работника в вызывающий поток.

На `InterruptDemo` обсуждаем кооперативную отмену: interrupt запрашивает остановку,
а код должен на неё отреагировать. Разбираем проверку флага и InterruptedException.
На границе Runnable после InterruptedException восстанавливаем флаг и выходим.

Затем показываем `HttpInterruptDemo`: HttpClient реагирует на прерывание ожидания,
а HttpURLConnection в нашем примере продолжает ждать ответ. Подчёркиваем, что поведение
определяется конкретным API; само слово «блокирующий» ничего не обещает об отмене.

### Этап 4. Согласование работы потоков (опционально, 0–5 мин)

Эту часть можно **объяснить верхнеуровнево или полностью отдать на самостоятельное изучение**.
Достаточно напомнить назначение synchronized, монитора и wait/notify, чтобы студенты
могли читать готовую реализацию. Подробный разбор и отдельная практика здесь не нужны.

Если обсуждаем на занятии, выделяем три правила: wait освобождает свой монитор и захватывает
его перед возвратом; notify не передаёт владение немедленно; условие ожидания проверяется
в while. Sleep монитор не освобождает. `AccountRaceDemo` и `WaitingDemo` оставляем
как дополнительные примеры для самостоятельного запуска или вопросов группы.

Если этап пропускаем, в JMM всё равно называем гарантию happens-before для одного и того же
монитора. В финальной практике используем код согласования как готовую часть каркаса.

### Этап 5. Java Memory Model: предпосылки и основные гарантии (~25 мин)

Начинаем с примера презентации: два потока записывают своё поле и читают чужое.
Просим предсказать результаты, отдельно обсуждаем пару (0, 0). Через кеши, буферы записей
и оптимизации компилятора/CPU подводим к JMM как контракту допустимого поведения программы.

Разделяем атомарность, видимость и порядок. Вводим happens-before и основные связи:
program order, тот же монитор, то же volatile-поле, start/join и транзитивность.
На примере публикации данных через флаг вместе собираем цепочку happens-before.
При необходимости показываем `PublicationDemo`; разбор не зависит от запуска jcstress.

Не объясняем volatile как «отключение кешей». Оно не делает составную операцию атомарной:
последовательность «прочитать — сравнить — записать» и инкремент требуют отдельного решения.
Не подводим к CAS через volatile. Экспериментальные результаты на слайдах иллюстрируют
поведение, но не заменяют обоснование по модели памяти.

### Этап 6. JMH и jcstress, дополнительные эксперименты (опционально, 0–10 мин)

Показ инструментов и их запуск **не входят в обязательную часть**. Можно кратко назвать
назначение и дать материалы на самостоятельное изучение: JMH — измерение производительности,
jcstress — поиск допустимых и запрещённых исходов конкурентного исполнения. Это разные задачи;
JMH не заменяет проверку корректности, а отсутствие ошибки в jcstress не является доказательством.
Отдельный JMH-бенчмарк для этого занятия не требуется.

Если есть время, открываем `DekkerPlain/Volatile` или `PublicationPlain/Volatile` и объясняем
State, Actor и Outcome. Лучше подготовить результаты заранее; живой запуск не должен быть
единственным способом показать редкий исход. Инструкция — в [«Эксперименты JMM»](Эксперименты%20JMM.md).

`IncrementPlain/Volatile` и `FinalPublication` оставляем дополнительными опытами по вопросам
группы: почему volatile не спасает ++, что даёт корректное конструирование и чем final-ссылка
отличается от неизменяемого объекта. При нехватке времени сразу переходим к практике.

### Этап 7. Постановка задачи и демонстрация реализации подписок (~20–35 мин)

**Задача.** Пользователь хочет получать котировки через заданный интервал в течение
ограниченного времени. При этом ввод должен оставаться доступным: можно добавить инструмент,
отменить подписку или выйти. Теперь показываем слайды с терминалом, архитектурой и временной
диаграммой; до этого момента проект не нужен для объяснения теории.

На `watch SBER 3s 30s` поясняем контракт: первый запрос готов сразу, следующие — через три секунды
после предыдущего ответа, срок подписки — тридцать секунд. `remove SBER` отменяет одну подписку
и её запрос, `exit` завершает весь сервис. Подробности — в [описании практики](Практика%20—%20подписки%20на%20котировки.md).

**Что делает семинарист.** Показывает готовое решение по частям либо дописывает небольшие методы
на подготовленном каркасе. За 20 минут достаточно разбора и запуска; расширенное время используем
для написания кода и ответов на вопросы. Прослеживаем следующие части решения:

1. `SubscriptionsCommand` читает stdin; `QuoteSubscriptionService` хранит подписки и запускает
   диспетчер; `TreiberThreadPool` создаёт фиксированное число работников. Работник выполняет запрос,
   но не спит между обновлениями — ожидание интервала относится к диспетчеру.
2. В `work` показываем получение задачи, выполнение, обработку RuntimeException и ожидание
   через park. Ошибка отдельной задачи не должна уничтожать работника. Автоматической замены
   работника после Error в учебной реализации нет.
3. Через `remove/close` и `shutdown/awaitTermination` связываем отмену запроса, interrupt и join.
   Volatile-флаг stopped обеспечивает видимость остановки. Код согласования через gate можно
   показать только на уровне назначения: общее состояние защищено, HTTP выполняется вне монитора.
4. **CAS и стек Трайбера — опционально.** Достаточно подсветить, что готовые `push/pop` используют
   AtomicReference.compareAndSet, чтобы конкурентные изменения вершины не теряли задачи.
   Подробности можно отдать на самостоятельное изучение. Если группа заинтересована, разбираем
   CAS-цикл и потерянный push; `TreiberPushPlain/Cas` показываем только при наличии времени.
   Отдельно проговариваем: volatile не реализует CAS, LIFO не гарантирует справедливость.
5. Запускаем mock-server с `MARKET_PULSE_MOCK_SCENARIO=slow` и `demo.Main` с аргументами
   `subscriptions --workers 3`. Добавляем две подписки, удаляем одну, проверяем продолжение второй
   и вызываем exit во время загрузки. Если остаётся время — показываем истечение срока и ошибку HTTP.

**Что делают студенты.** Предлагают распределение работы между потоками, объясняют, где нужны
ожидание и отмена, предсказывают поведение команд и проверяют контракт вместе с семинаристом.
Самостоятельное написание отдельных методов возможно по уровню группы, но не обязательно;
реализацию всего пула и сервиса с нуля не задаём в рамках основного тайминга.

В финале связываем наблюдаемое поведение с теорией: число загрузок ограничено работниками,
запросы одной подписки не перекрываются, отмена поддерживается выбранным HTTP-клиентом.
Завершаем вопросом, какие части этой инфраструктуры хотелось бы заменить стандартной библиотекой.
Это переход к Executor Framework на следующем семинаре.

## Референсы для семинариста

### Статьи

- [Глубокое погружение в Java Memory Model — blinky-z, Хабр](https://habr.com/ru/articles/685518/) —
  основной русскоязычный разбор предпосылок, порядка и экспериментов.
- [JSR-133 FAQ — Jeremy Manson, Brian Goetz](https://www.cs.umd.edu/~pugh/java/memoryModel/jsr-133-faq.html) —
  объяснение гарантий volatile, final и синхронизации от участников разработки модели.
- [Java Memory Model Pragmatics — Aleksey Shipilёv](https://shipilev.net/blog/2014/jmm-pragmatics/) —
  подробный конспект доклада: атомарность, HB и ограничения интуитивных моделей.
- [Safe Publication and Safe Initialization — Aleksey Shipilёv](https://shipilev.net/blog/2014/safe-public-construction/) —
  подготовка к вопросам о публикации объектов и final.

### Видео на YouTube

- [Алексей Шипилёв — «Прагматика Java Memory Model», часть 1](https://www.youtube.com/watch?v=noDnSV7NCtw).
- [Тот же доклад, часть 2](https://www.youtube.com/watch?v=Ky1_5mabd18) — смотреть как единый разбор модели.
- [Алексей Шипилёв — Bullet-Proof Java Concurrency](https://www.youtube.com/watch?v=8lHAcetqQ5c) —
  дополнительный доклад о проверке корректности конкурентного кода; полезен перед показом jcstress.

Видеоссылки взяты с [авторской страницы докладов](https://shipilev.net/).
Доклады исторические: актуальные детали Thread API и реализации JVM сверять с документацией JDK 25.

### Спецификация и инструменты

- [JLS 17: Threads and Locks](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html) —
  основание для гарантий HB, мониторов и final.
- [Thread](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html) и
  [Thread.State](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.State.html) —
  жизненный цикл и контракт interrupt/join.
- [LockSupport](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/LockSupport.html) и
  [AtomicReference](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/atomic/AtomicReference.html) —
  permit, park/unpark и эффекты памяти CAS.
- [OpenJDK jcstress](https://github.com/openjdk/jcstress) — инструмент и примеры; эксперименты
  семинара лежат в модуле `jcstress`. Перед занятием собрать `mvn -pl jcstress -am package -DskipTests`
  и подготовить отчёт по локальной инструкции выше.
