# Семинар 10. Платформенные потоки и Java Memory Model

## План семинара

| # | Этап | Время |
|---|---|---:|
| 1 | Постановка задачи: временные подписки на котировки | ~5 мин |
| 2 | Потоки Java и ОС: жизненный цикл и состояния | ~12 мин |
| 3 | Thread API: создаём работников и диспетчер | ~8 мин |
| 4 | Исключения и прерывание: отменяем загрузку и завершаем сервис | ~15 мин |
| 5 | Мониторы и ожидание: координируем подписки и работников | ~10 мин |
| 6 | Предпосылки JMM, happens-before и публикация | ~15 мин |
| 7 | CAS и стек Трайбера: передаём задачи работникам | ~15 мин |
| 8 | Дополнительные JMM-эксперименты и обсуждение | до ~30 мин |
| 9 | Итоговый запуск подписок, вопросы и мост к Executor Framework | ~10 мин |

Итого **90–120 минут**. В коротком варианте этап 8 пропускаем. Один пример развивается
по ходу презентации; отдельные демо используем для изолированных свойств.

### 1. Постановка задачи (~5 мин)

**Задача:** пользователь задаёт тикер, интервал и срок подписки, получает котировки в фоне
и продолжает вводить команды. На слайдах после плана разобрать `watch SBER 3s 30s`,
`remove SBER`, `exit` и схему «ввод → диспетчер → стек → N работников».

**Смотреть:** `SubscriptionsCommand.call`; полный контракт — в [описании практики](Практика%20—%20подписки%20на%20котировки.md).
Первый запрос готов сразу; интервал — после ответа, одна загрузка на подписку. По временной
диаграмме показать: ожидание следующего обновления не занимает работника. Пока только
обозначить компоненты, не погружаться в CAS. Итоговая реализация уже есть в исходниках;
на переходах в IDE разбираем или дописываем отдельные методы.

### 2. Жизненный цикл и состояния (~12 мин)

**Обсудить:** платформенная модель 1:1, краткий ориентир на виртуальные M:N; состояния NEW,
RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED. Daemon — отдельная характеристика.

**Смотреть:** `ThreadStatesDemo`, при необходимости — `jcmd <pid> Thread.print`.
Связать с задачей: ввод ждёт stdin, диспетчер — срок, работник — задачу или HTTP-ответ.
**Акцент:** RUNNABLE не означает обязательное потребление CPU; JVM и ОС описывают разные
состояния. BLOCKED относится к монитору. Спящий worker не занимает ядро постоянно,
но spinning, пробуждения и переключения имеют стоимость. getState — снимок, не средство управления.

### 3. Создаём исполнителей (~8 мин)

**Повторить:** Runnable, конструктор/builder, start против run, join и однократность запуска.
`ThreadApiDemo` — короткое напоминание, затем сразу к нашему коду.

**Смотреть:** конструктор `TreiberThreadPool`, массив workers и конструктор
`QuoteSubscriptionService`. Разобрать создание N платформенных работников и отдельного dispatcher.
**Акцент:** поток выполняет много задач, задача не создаёт новый поток. HTTP выполняется
работником, а ожидание интервала — диспетчером. Детали стека пока рассматриваем как готовый контракт push/pop.

### 4. Ошибки, отмена и завершение (~15 мин)

**Смотреть сначала:** `UncaughtExceptionDemo`, затем `TreiberThreadPool.work`.
Разобрать finally → handler → TERMINATED; индивидуальный обработчик либо делегирование
через ThreadGroup/default. Handler не продолжает выполнение и не заменяет finally;
join не перебрасывает ошибку работника. В пуле RuntimeException задачи изолируется,
а автоматической замены worker после необработанного Error пока нет.

**Затем:** `InterruptDemo` и `HttpInterruptDemo`. Сравнить флаг, InterruptedException,
park и непрерываемый вход в монитор. HttpClient.send поддерживает отмену, обычный
HttpURLConnection на платформенном потоке может продолжить чтение.

**Вернуться к задаче:** `QuoteSubscriptionService.remove/close`, `TreiberThreadPool.shutdown/awaitTermination`.
Remove отменяет одну подписку; exit — весь сервис. Пройти interrupt/unpark → выход → join.
**Акцент:** отмена кооперативная; после InterruptedException обычно восстанавливаем флаг и выходим.
Остановка нашего пула отбрасывает накопленные задачи — это ещё не семантика ExecutorService.shutdown.

### 5. Координация и ожидание (~10 мин)

**Кратко:** монитор, synchronized, wait/notify. `AccountRaceDemo` — иллюстрация защиты всей
операции; `WaitingDemo` — sleep удерживает монитор, wait освобождает свой и затем захватывает
его снова. Notify не передаёт монитор, условие проверяется в while.

**Смотреть в задаче:** `QuoteSubscriptionService.dispatch/refresh` — gate защищает сроки
и inFlight; HTTP идёт вне монитора, completion задаёт nextRun и уведомляет диспетчер.
Затем `TreiberThreadPool.work/submit` и при необходимости `ParkingDemo`.
**Акцент:** park/unpark работает через один ненакопительный permit; нужны повторные проверки.
Публикация между пустым pop и park не теряет пробуждение. Yield — только подсказка планировщику.

### 6. JMM и публикация (~15 мин)

**Начать с вопроса презентации:** два потока записывают своё поле и читают чужое — возможны ли
два нуля? В IDE открыть `DekkerPlain`, объяснить Actor/State/Outcome и посмотреть заранее
подготовленный jcstress-результат. Инструкция — в [«Эксперименты JMM»](Эксперименты%20JMM.md).

**Обсудить:** регистры, кеши, буферы записей, оптимизации JIT/CPU → необходимость контракта JMM.
Развести атомарность, видимость и порядок. Разобрать HB: program order, тот же монитор,
то же volatile-поле, start/join, транзитивность.

**Смотреть:** `DekkerVolatile`, `PublicationDemo`, `PublicationPlain/Volatile`.
**Акцент:** volatile не «отключает кеши»; данные публикуются цепочкой через флаг. Sleep не заменяет
join, обычный spin может не закончиться. Ненаблюдение ошибки в тесте не доказывает корректность;
jcstress исследует исходы, JMH измеряет производительность. В нашем пуле stopped нужен для
видимости отмены, а передача самой задачи разбирается на следующем этапе.

### 7. CAS и передача задач (~15 мин)

**Бизнес-задача этапа:** ввод/диспетчер публикует работу, несколько работников извлекают её
без потери задач. Открыть `TreiberStack.push/pop`: immutable Node, AtomicReference head,
CAS-цикл с повтором при изменившейся вершине. Связать с submit и worker, затем проговорить
цепочку «создали задачу → опубликовали узел → другой поток извлёк → выполнил».

**Смотреть:** `TreiberPushPlain/TreiberPushCas` — сначала прогноз, затем исходы.
Plain-push может потерять задачу; один volatile-head не делает push атомарным. Для отдельной
видимости служит пара PublicationPlain/Volatile. AtomicReference уже даёт нужные гарантии памяти.
**Акцент:** узлы не переиспользуются; CAS-стек не превращает весь пул в lock-free — lifecycle
согласован монитором. LIFO отдаёт приоритет новым задачам и не гарантирует справедливость.

### 8. Дополнительные эксперименты (до ~30 мин)

**Если есть время:** `IncrementPlain/Volatile` — потерянный ++; `FinalPublication` — гарантии
корректного конструирования без утечки this. Final-ссылка не делает mutable-содержимое неизменяемым.
Вернуться к worker: почему очистка флага после задачи не теряет stopped и не позволяет park
превратиться в busy-loop; как remove согласует runner и отмену под одним монитором.
Обсуждение строить от прогнозов группы, не от количества успешных повторов.

### 9. Итоговый запуск (~10 мин)

**Запустить:** mock-server, `demo.Main` с `subscriptions --workers 3`,
`MARKET_PULSE_MOCK_SCENARIO=slow`. Ввести две подписки, дождаться цен, выполнить remove
одной и убедиться, что вторая продолжается; затем exit во время загрузки.
Срок отдельной короткой подписки должен остановить новые запросы, ошибка — не убить остальных.

**Проверить по коду:** не более N загрузок, отсутствие перекрытия одной подписки,
пропуск просроченной задачи из стека и поддержка прерывания HttpClient. Текущий endpoint
возвращает весь каталог: каждый refresh выбирает нужную цену из отдельного ответа.
Реализацию пула можно отдать студентам, если позволяет уровень; иначе семинарист разбирает готовую.

**Завершить:** на 11-м сохраняем сценарий и рефакторим пул/диспетчер на ExecutorService
и ScheduledExecutorService; отдельно сравним LIFO/FIFO, отмену и политики shutdown.

## Референсы для семинариста

### Статьи

- [Глубокое погружение в Java Memory Model — blinky-z, Хабр](https://habr.com/ru/articles/685518/) —
  основной русскоязычный разбор предпосылок, порядка и экспериментов.
- [JSR-133 FAQ — Jeremy Manson, Brian Goetz](https://www.cs.umd.edu/~pugh/java/memoryModel/jsr-133-faq.html) —
  объяснение гарантий volatile, final и синхронизации от участников разработки модели.
- [Java Memory Model Pragmatics — Aleksey Shipilёv](https://shipilev.net/blog/2014/jmm-pragmatics/) —
  подробный конспект доклада: атомарность, HB и ограничения интуитивных моделей.
- [Safe Publication and Safe Initialization — Aleksey Shipilёv](https://shipilev.net/blog/2014/safe-public-construction/) —
  подготовка к вопросам о публикации объектов и final.

### Видео на YouTube

- [Алексей Шипилёв — «Прагматика Java Memory Model», часть 1](https://www.youtube.com/watch?v=noDnSV7NCtw).
- [Тот же доклад, часть 2](https://www.youtube.com/watch?v=Ky1_5mabd18) — смотреть как единый разбор модели.
- [Алексей Шипилёв — Bullet-Proof Java Concurrency](https://www.youtube.com/watch?v=8lHAcetqQ5c) —
  дополнительный доклад о проверке корректности конкурентного кода; полезен перед показом jcstress.

Видеоссылки взяты с [авторской страницы докладов](https://shipilev.net/).
Доклады исторические: актуальные детали Thread API и реализации JVM сверять с документацией JDK 25.

### Спецификация и инструменты

- [JLS 17: Threads and Locks](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html) —
  основание для гарантий HB, мониторов и final.
- [Thread](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html) и
  [Thread.State](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.State.html) —
  жизненный цикл и контракт interrupt/join.
- [LockSupport](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/LockSupport.html) и
  [AtomicReference](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/atomic/AtomicReference.html) —
  permit, park/unpark и эффекты памяти CAS.
- [OpenJDK jcstress](https://github.com/openjdk/jcstress) — инструмент и примеры; эксперименты
  семинара лежат в модуле `jcstress`. Перед занятием собрать `mvn -pl jcstress -am package -DskipTests`
  и подготовить отчёт по локальной инструкции выше.
