# Семинар 10. Платформенные потоки и Java Memory Model

**Тема модуля:** Многопоточность

**Тема семинара:** устройство платформенных потоков, статусная модель JVM и ОС, ожидание и
кооперативное прерывание; предпосылки JMM, happens-before и безопасная публикация.

---

## Краткое содержание

**На начало семинара:** Thread API студентам знаком. На семинаре 7 разобраны блокирующий
и неблокирующий I/O; в проекте есть блокирующий HttpClient к mock-server.

**На семинаре:** кратко повторяем API и углубляемся в поведение: кто планирует поток, почему он
перестаёт исполняться, как его разбудить и отменить. Через кэши, буферы записей и оптимизации
переходим к модели памяти. Теорию сопровождают отдельные демо и jcstress-тесты.

**На конец семинара:** студенты объясняют ожидание на уровнях JVM/ОС, реакцию на interrupt
и цепочки happens-before. В проекте работает фоновое обновление согласованного снимка котировок:
пользователь читает старый полный снимок, пока новый загружается; exit отменяет обновление.

Презентация — теория; исходники открываем в IDE на перебивках. Бизнес-задача появляется после
теории. Самостоятельная реализация не обязательна: показываем и обсуждаем готовый код.

### Этап 1. Виды и жизненный цикл (~15 мин)

**Слайды 4–8.** Сохраняем старую последовательность: виды потоков → жизненный цикл → планировщик
и состояния. Сопоставляем платформенную модель 1:1 с будущим разговором о виртуальной M:N.
Java-поток, поток ОС и ядро CPU — разные сущности. Приоритет не гарантирует порядок исполнения.

`ThreadStatesDemo`: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
Показать `jcmd <pid> Thread.print`. Ready и Running входят в JVM RUNNABLE; блокирующий read
может оставаться RUNNABLE в Java, хотя поток ОС ожидает I/O. getState — моментальное наблюдение,
а не средство управления. Конкретная картина зависит от API и JDK.

> **Вопрос группе:** RUNNABLE обязательно занимает CPU? BLOCKED означает любую блокировку?

### Этап 2. Работа с потоками (~35 мин)

**Слайды 9–15.** Кратко повторить Runnable, start/run, конструктор и builder, daemon, sleep и join.
Конструктор Thread не устарел. Повторный start запрещён; вызов run не создаёт поток.
`ParkingDemo`: коротко показать park/unpark и одно ненакопительное разрешение; условие проверяется
в цикле из-за ложных возвратов и interrupt. Перед unpark целевой поток запускаем.
Это знакомство с механизмом ожидания, не реализация синхронизатора.

На API и парковку — около 10 минут, на прерывание и исключения — около 20, на вопросы — 5.
В демо исключений достаточно одного запуска и обсуждения вывода.

`InterruptDemo` и `BlockingIoDemo`. Сопоставить вычисление, sleep, park, монитор и выбранный I/O.
При InterruptedException флаг очищается; park возвращается с установленным флагом; вход
в монитор не прерывается. Legacy Socket.read не обещает выход от Thread.interrupt — освобождаем
ресурс через close; выбранный HttpClient.send умеет реагировать на прерывание.
Не обобщать поведение одного API на все I/O. stop/suspend/resume не используем.

**Необработанное исключение:** `UncaughtExceptionDemo` (~3 мин внутри этапа).
Если Throwable проходит все обработчики и выходит из run(), стек работника раскручивается:
выполняются finally-блоки и освобождаются мониторы при выходе из synchronized. Затем JVM вызывает
UncaughtExceptionHandler в том же падающем потоке. После возврата обработчика поток завершается;
продолжить выполнение с места ошибки или повторно запустить этот Thread нельзя.
Другие потоки автоматически не завершаются. start() и join() не перебрасывают ошибку работника
в вызывающий поток; ошибка main может завершить приложение лишь в зависимости от оставшихся
non-daemon потоков, а не потому, что вся JVM обязана упасть от исключения любого потока.

Настройка: setUncaughtExceptionHandler / builder.uncaughtExceptionHandler для конкретного потока;
при отсутствии явной настройки действует ThreadGroup, который может делегировать глобальному
setDefaultUncaughtExceptionHandler. Стандартный путь обычно выводит стек в stderr. Исключение
из самого uncaughtException игнорируется JVM. Это последняя точка наблюдения/логирования,
не механизм восстановления продолжения. В демо глобальный обработчик обязательно восстанавливается.
На исключения отвести около 3 минут из блока прерывания и завершения; общий час на потоки сохраняем.


### Этап 3. Синхронизация (~10 мин)

**Слайды 16–22, переход 24.** Начать со старой иллюстрации двух списаний.
**Задача:** не позволить двум запросам успешно списать средства, если денег хватает только одному.
`AccountRaceDemo`: обе проверки видят старый баланс, затем происходят два успешных списания;
во втором варианте проверка и изменение защищены одним synchronized-блоком.
Фиксируем, что отдельно защищённые чтение и запись не защищают всю операцию.

Кратко напомнить монитор объекта, владельца, entry set и wait set; не разбирать внутреннее устройство
мониторов HotSpot. У экземпляра и класса разные мониторы. В `WaitingDemo` сравнить sleep и wait:
sleep не отдаёт монитор; wait отдаёт свой монитор и перед возвратом захватывает его снова.
notify не передаёт монитор немедленно. Условие проверяем в while, вызовы требуют владения тем же монитором.
Обзор синхронизаторов и concurrent-коллекций оставляем следующим занятиям.

### Этап 4. Эксперимент и предпосылки JMM (~10 мин)

**Слайды 25–35.** Сначала старый вопрос с двумя полями: группа предсказывает исходы, включая (0, 0).
Показать DekkerPlain и подготовленный jcstress-отчёт. Не объяснять результат только перестановкой строк:
исход без единого последовательного чередования тоже допустим. Затем перейти к причинам и JMM.
Вместо sleep для ожидания окончания эксперимента используем jcstress; в обычных демо — join.

Теория по статье и схемам прошлого года. Ядра, регистры, кэши, cache coherence, буферы записей;
затем оптимизации JIT и процессора. Согласованность кешей не превращает все обращения разных
потоков в единый порядок. Не учить «volatile просто сбрасывает кеш».
JMM определяет допустимые выполнения Java-программы, не конкретную схему аппаратной памяти.
Java Process Memory Model из семинара 1 и JMM — разные темы.

### Этап 5. Гарантии и публикация (~10 мин)

**Слайды 36–41.** Сохраняем связку: volatile в первом опыте → ResultProvider с обычным флагом →
volatile-флаг → цепочка happens-before. Рядом показываем DekkerVolatile и PublicationPlain / Volatile.
Обычный флаг исследуем в jcstress, чтобы не зависнуть при показе в IDE.

Различить атомарность, видимость и порядок. Разобрать program order, monitor unlock/lock,
volatile write/read, start и join, транзитивность happens-before. Это отношение между действиями,
не наблюдаемый порядок по часам. volatile не делает counter++ атомарным.
`PublicationDemo` показывает безопасную публикацию данных через флаг; бесконечный spin
с обычным флагом не запускать в основном процессе семинара.

### Этап 6. Согласованный снимок (~10 мин)

После теории — новая прикладная часть; в исходной презентации её нет.

**Задача, которую решаем.** Пользователь хочет видеть последние доступные котировки,
пока сервис получает новые. Нельзя выдавать новый номер версии со старыми ценами или
частично заполненный набор. Сетевое ожидание не должно блокировать чтение старого снимка.

Показать `snapshot.MarketSnapshot`, `SnapshotService`, `cli.SnapshotCommand`.
Единственный фоновый писатель собирает новый неизменяемый снимок локально и публикует одной
записью volatile-ссылки. Читатель сохраняет ссылку в локальную переменную и читает одну версию.
Для первой загрузки есть короткий мониторный протокол awaitFirst: condition loop и notifyAll;
сам HTTP выполняется вне монитора. CLI не ждёт первую загрузку: show сообщает, если данных пока нет.

Ошибка загрузки оставляет прежний полный снимок. exit прерывает работника и ждёт завершения.
Данные снимка — копии цен (BigDecimal), не ссылки на изменяемый каталог Instrument.
Демо неправильной публикации остаётся в jcstress, в рабочую команду ошибочный вариант не включаем.

В этапах 4–5 запустить один выбранный jcstress-тест, остальные результаты открыть из заранее
сохранённого отчёта. Отсутствие редкого исхода не доказывает невозможность. После проекта
вернуться к прогнозам группы и кратко подвести итоги.

### Этап 7. Углубление (до ~30 мин)

Дополнительные jcstress-опыты: потерянный инкремент обычного и volatile счётчика, final-поля и
публикация, подробный разбор разрешённых результатов. Сначала прогноз группы, затем классификация,
затем эксперимент. jcstress проверяет исходы, JMH измеряет производительность — не подменять одно другим.
Обсудить, почему unit-тест с миллионом повторов не доказывает корректность конкурентного кода.
