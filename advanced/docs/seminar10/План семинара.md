# Семинар 10. Платформенные потоки и Java Memory Model

**Тема модуля:** Многопоточность

**Тема семинара:** устройство платформенных потоков, жизненный цикл, ожидание и кооперативная
отмена; предпосылки Java Memory Model, happens-before и безопасная публикация.

---

## Краткое содержание

**На начало семинара:** студентам знаком Thread API. На семинаре 7 разобраны блокирующий
и неблокирующий I/O; в проекте есть блокирующий HttpClient к mock-server.

**На семинаре:** по презентации повторяем API и разбираем детали потоков и JMM. В нужные моменты
открываем короткие демо в IDE. После всей теории применяем гарантии публикации к фоновому
обновлению котировок.

**На конец семинара:** студенты различают состояния JVM и ОС, объясняют реакцию ожиданий на
interrupt и обосновывают публикацию через happens-before. В проекте работает согласованный
снимок: show читает последнюю полную версию, exit отменяет обновление и ждёт завершения работника.

### Этап 1. Презентация и демонстрации (~80–110 мин)

**Задача этапа:** выстроить модель поведения потоков и научиться объяснять корректность
межпоточного взаимодействия. Презентация задаёт последовательность, демо подтверждают конкретные
тезисы; запускать подряд весь каталог примеров не нужно.

**1.1. Виды потоков и жизненный цикл (~15 мин).**

Обсудить 1:1 для платформенных потоков и кратко обозначить будущую тему виртуальных M:N.
Daemon — независимая характеристика; Java-поток, поток ОС и ядро CPU — разные сущности.
Рассмотреть NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.

**На что смотреть:** Ready/Running входят в JVM RUNNABLE. Поток ОС может ждать I/O, хотя Java
показывает RUNNABLE. BLOCKED — вход/повторный вход в монитор, не любое блокирующее ожидание.
Припаркованный поток не занимает CPU постоянно, но попытки захвата, spinning и пробуждения
имеют стоимость. getState — моментальный снимок, а не средство управления.

**Демо:** при разборе жизненного цикла открыть `ThreadStatesDemo`; при необходимости показать
`jcmd <pid> Thread.print`. В разговоре об управлении ожиданием — `ParkingDemo`: один permit,
unpark до park уже запущенного потока, ненакопление разрешений, повторная проверка условия.
Yield — подсказка планировщику, не гарантия передачи управления и не кооперативная модель.

**1.2. Создание, завершение и прерывание (~35 мин).**

Кратко повторить Runnable, конструктор/builder, run/start, sleep/join, daemon и приоритет.
`ThreadApiDemo` показывает обычный вызов run, запуск через start, запрет повторного start,
unstarted и видимость результата после join. Приоритет не гарантирует долю CPU или порядок.

Затем исключения: раскрутка стека, finally, освобождение мониторов, UncaughtExceptionHandler,
завершение. Handler выполняется в падающем потоке, не продолжает выполнение после ошибки и не
заменяет finally. Start/join не перебрасывают ошибку работника в main.

**Демо:** `UncaughtExceptionDemo` — индивидуальный обработчик, затем ThreadGroup с делегированием
родителю/default. Это альтернативный выбор/делегирование, а не обязательный вызов всех handler.
Глобальная настройка в конце восстанавливается. Другие потоки не обязаны завершаться от ошибки.

Прерывание — запрос отмены, который должен поддержать исполняемый код. На границе Runnable
при InterruptedException восстановить флаг и выйти; не продолжать цикл как будто отмены не было.

**На что смотреть:** isInterrupted читает флаг; Thread.interrupted читает и очищает флаг текущего
потока. Sleep/wait/join бросают InterruptedException с очисткой флага; park возвращается с флагом;
вход в synchronized от interrupt не отменяется. Stop/suspend/resume не используем.

**Демо:** `InterruptDemo`, затем `HttpInterruptDemo`. Локальный сервер удерживает тело ответа:
HttpClient.send выходит с InterruptedException, а HttpURLConnection на платформенном потоке
продолжает чтение и затем возвращает ответ с установленным флагом. Без аргументов — оба опыта;
аргументы `http-client` / `url-connection` выбирают один. Отмена ожидания не откатывает работу
сервера. `BlockingIoDemo` — дополнительный низкоуровневый опыт с Socket.read и close; в коротком
варианте достаточно HTTP-сравнения. Не переносить контракт одного I/O API на остальные.

**1.3. Кратко о синхронизации (~10 мин).**

**Задача примера:** не допустить два успешных списания, если денег хватает только одному.
На иллюстрации счёта обсудить гонку, затем показать `AccountRaceDemo`: отдельно защищённые
действия не защищают всю проверку с изменением; нужен один общий монитор на операцию.

Напомнить владельца монитора, entry set / wait set, synchronized-блок/метод. У экземпляра
и класса разные мониторы. Внутреннее устройство мониторов HotSpot не разбираем подробно.

**Демо:** `WaitingDemo` при переходе к wait/notify. Sleep сохраняет удерживаемый монитор,
wait освобождает свой и перед возвратом захватывает его снова. Notify не передаёт монитор
немедленно. Условие проверяется в while; вызовы требуют владения тем же монитором.

**1.4. JMM: эксперимент, предпосылки и публикация (~20 мин).**

Начать с вопроса презентации: два потока записывают своё поле и читают чужое. Группа прогнозирует
разрешённые исходы, затем открываем `DekkerPlain` и подготовленный jcstress-отчёт.
Не использовать sleep(100) со старых скриншотов как гарантию завершения работников.

Через регистры, кеши, буферы записей и оптимизации JIT/CPU объяснить предпосылки JMM. Coherence
не задаёт общий порядок по всем переменным; volatile не «отключает кеши». Наблюдение двух нулей
не доказывает конкретную перестановку машинных инструкций. JMM задаёт допустимое поведение,
а не устройство аппаратной памяти и не раскладку heap/stack.

**На что смотреть:** атомарность, видимость и порядок — разные свойства. Data race — конфликтующие
доступы без HB. Разобрать program order, unlock/lock того же монитора, volatile write/read того же
поля, start/join и транзитивность. HB — отношение между действиями, не сравнение часов в логах.

**Демо:** `DekkerVolatile` запрещает (0,0). Затем `PublicationDemo` с ResultProvider и
`PublicationPlain` / `PublicationVolatile` в jcstress: данные → volatile-флаг → чтение флага → данные.
Бесконечный plain-spin из презентации не запускать в основном процессе занятия.
Сначала прогноз, затем объяснение по модели, затем наблюдаемые результаты. Ненаблюдение исхода
не доказывает невозможность. Jcstress проверяет конкурентные исходы, JMH измеряет производительность.

**1.5. Дополнительные вопросы JMM (до ~30 мин, если есть время).**

`IncrementPlain` / `IncrementVolatile`: volatile не делает ++ атомарным. `FinalPublication`:
специальные гарантии final при корректном конструировании не делают mutable-содержимое
неизменяемым. Конструктор не должен публиковать this. Подробно разобрать разрешённые исходы,
сравнить plain/volatile и обсудить, почему миллион повторов unit-теста не доказывает корректность.
Все эти вопросы завершаем до прикладной части.

### Этап 2. Согласованный снимок котировок (~10 мин)

**Бизнес-задача:** пользователь хочет видеть последние доступные котировки, пока сервис
загружает новые. Нельзя выдавать номер новой версии со старыми ценами или частично заполненный
набор. Сетевое ожидание не должно блокировать чтение предыдущего полного снимка.

Перед завершающими слайдами остановить показ и открыть `MarketSnapshot`, `SnapshotService`,
`SnapshotCommand`. Самостоятельная реализация не обязательна: семинарист показывает готовый код.

**На что смотреть:** один writer собирает immutable-снимок локально и публикует одной записью
volatile-ссылки. Reader один раз сохраняет ссылку локально и читает одну версию. Карта копируется,
значения BigDecimal неизменяемы; ссылки на изменяемые Instrument в снимок не попадают.

Для первой загрузки есть короткий протокол awaitFirst с while/notifyAll; HTTP идёт вне монитора.
CLI не блокируется на первой загрузке: show сообщает, если данных пока нет. Ошибка загрузки
сохраняет предыдущий снимок. Exit прерывает worker и ждёт завершения; выбранный HttpClient
поддерживает прерывание, поэтому отмена не ждёт получения всего ответа.

**Показ:** запустить snapshot с медленным mock-server → show во время загрузки → show после
публикации → show во время следующей загрузки возвращает старую целую версию → exit отменяет
работника. Обосновать публикацию цепочкой HB, затем вопросы/обратная связь/завершение.
