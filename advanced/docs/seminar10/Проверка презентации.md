## Содержательные замечания

| Слайд | Замечание и предлагаемая поправка |
|---|---|
| 2 | Остались номера 12/13. Для текущего модуля следующие занятия — 11/12. Java 19 можно оставить только с пометкой preview: финальный API виртуальных потоков появился в 21. |
| 5 | Формулировка «на один kernel thread от одного до нескольких пользовательских» слишком общая: соответствие задаётся моделью 1:1, N:1 или M:N. Kotlin-корутины не являются Java Thread и не тождественны виртуальным потокам; оставить как аналогию пользовательского планирования. Исправить «гоуртины» → «горутины», «до несколько» → «до нескольких». |
| 6 | Daemon — независимая характеристика. Платформенные потоки бывают daemon/non-daemon; виртуальные всегда daemon. Дерево на картинке может создать впечатление, что daemon — отдельный вид только старых потоков. |
| 7 | В картинке неоднозначные стрелки «thread terminated» из ожиданий. Завершение B при A.join(B) будит A, а не завершает его. После wait, включая timeout/interrupt, требуется повторно захватить монитор. Подробные пояснения включены в план. |
| 9 | У WAITING подпись повторяет sleep(timeout); заменить на Object.wait(), Thread.join(), LockSupport.park(). Sleep с положительным сроком относится к TIMED_WAITING. BLOCKED — именно вход/повторный вход в монитор, не любая блокирующая операция. |
| 10 | Thread.wait как статического API нет: wait наследуется от Object и вызывается на объекте при владении его монитором. Yield лишь подсказка; нельзя обещать управление состоянием или кооперативную модель. Park не обещает ждать до unpark: interrupt и ложный возврат тоже допустимы. На схеме «припаркован — не тратит CPU» относится к реальному сну, не ко всем служебным этапам вызова. |
| 12 | Конструктор Thread — действующий API, не deprecated. Лучше «создание через конструктор». Runnable здесь нормальный контракт задачи; не связывать наличие интерфейса только с обратной совместимостью. |
| 14 | Приоритет не гарантирует больше ресурсов или порядок исполнения. Указать диапазон 1–10 и зависимость эффекта от ОС/планировщика. |
| 16 | Стрелка «работа была прервана → Terminated» неверна без реакции кода. Заменить на «код обработал запрос отмены и вышел из run». |
| 17 | Handler не аналог finally: при нормальном завершении он не вызывается. Ресурсы освобождаем в finally/try-with-resources. Handler наблюдает необработанный Throwable после раскрутки стека; сам тоже может выполнять код. Не смешивать исключение с Java interrupt. |
| 18 | Это выбор/делегирование обработчика, не обязательная цепочка вызовов всех обработчиков. Индивидуальный handler, если задан, вызывается вместо ThreadGroup; группа по умолчанию делегирует родителю, корневая — default, а при его отсутствии печатает stderr (особый случай ThreadDeath). Если custom handler/group не делегирует, дальнейших вызовов нет. |
| 19–20 | Interrupt — запрос отмены/флаг, а InterruptedException — реакция некоторых операций. Не обязательно «системный метод» и не обязательно именно InterruptedException: park возвращается, SocketChannel бросает ClosedByInterruptException, обычный Socket на платформенном потоке может продолжать чтение. HTTP-сравнение есть в демо. |
| 28 | Notify будит один произвольно выбранный поток из wait set, notifyAll — все. Они не передают монитор. После пробуждения нужен повторный захват и проверка условия в while. Достаточно владеть монитором; это может быть synchronized-метод, не только явно написанный блок. |
| 32–35 | Sleep(100) в обвязке не гарантирует окончания worker и не обеспечивает публикацию results. Для корректного чтения нужны join обоих работников либо jcstress. Вопрос лучше «какие исходы разрешены», а не «встретились ли они за 1000 запусков». Код опытов в репозитории использует jcstress. |
| 35 | В логе (1,1) встретился 424 раза, а (0,0) — 2 раза. Текст «ни одной … оба проинициализированы» противоречит логу; редкий исход здесь — оба чтения вернули 0. Один такой лог не доказывает конкретное переупорядочивание CPU. |
| 36–37 | Причины — оптимизации компилятора/CPU, буферы и видимость. ОС планирует потоки, но её не следует называть основным автором перестановок машинных инструкций. Coherence не заменяет порядок между разными адресами. |
| 40 | Диаграмма содержит перестановки чтение/запись внутри actor. Это иллюстрации возможного наблюдаемого поведения, а не только последовательные чередования исходного program order. Кеши не обязаны быть «неконсистентными»: coherence и memory ordering решают разные задачи. |
| 41 | Отсутствие (0,0) обосновывается моделью для двух volatile-полей, а не успешным тестом. Дополнить устно: volatile не делает ++ атомарным. Исправить «семнатике». |
| 42–45 | Публикация через флаг подходит для одноразовой передачи без дальнейших перезаписей result. Нужна сводка HB: тот же монитор, то же volatile-поле, start/join, транзитивность. Существующий бесконечный plain-spin не запускать в главном процессе занятия; ошибку изучать в jcstress. |

## Показ и оформление

- На 7-м слайде схема очень плотная; для детального разбора лучше открыть крупнее в IDE/просмотрщике.
- Код на 42-м, текстовые скриншоты на 17/19 и лог на 35-м мелкие для аудитории: показывать в IDE.
- В этой редакции снова есть чтение (29, 46); ранее договаривались выдавать материалы отдельно. В плане это необязательные остановки, не отдельные этапы занятия.
- 47 — обратная связь, 48 — спасибо, 49 — дополнительная заставка. Технических пустых слайдов нет; для живого показа завершать на 48-м либо использовать 49 как фон.
- Шрифты в LibreOffice подменяются; рендер не гарантирует полного совпадения с PowerPoint. Крупного обрезанного текста в просмотренном рендере не обнаружено.
