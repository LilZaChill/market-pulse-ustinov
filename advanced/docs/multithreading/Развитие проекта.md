# Развитие Market Pulse в модуле многопоточности

Продвинутый трек, семинары 10–12. Связь бизнес-задач с темами — в дополнение к
[плану модуля](README.md). Семинар 10 уже реализован; задачи 11–12 — предложения для подготовки,
а не описание существующих возможностей. Детали CLI и контрактов уточним в планах занятий.

## Семинар 10. Последние котировки доступны, пока загружаются новые

**Бизнес-задача:** пользователь хочет смотреть котировки, не ожидая каждого сетевого обновления.
Данные должны относиться к одной версии; ошибка новой загрузки не должна уничтожать предыдущие.

**Уже добавлено:** команда `snapshot` с вводом `show` / `exit`. Один фоновый платформенный поток
периодически загружает данные и публикует полный снимок: версия, время и карта цен.
Во время загрузки show возвращает предыдущую версию; до первой загрузки сообщает, что данных нет.
Ошибка сохраняет старый снимок и доступна для отображения. Exit отменяет worker и ждёт его завершения.
Медленный сценарий mock-server позволяет увидеть ожидание сети.

| Требование | Какую тему закрываем |
|---|---|
| Обновление не блокирует пользовательский ввод | Создание платформенного потока, разделение работы между потоками |
| Читатель получает целую версию | Immutable-снимок, копирование карты, volatile-ссылка и happens-before |
| При необходимости дождаться первой версии | awaitFirst: монитор, wait в while, notifyAll; этот метод есть в сервисе, CLI его не вызывает |
| Завершиться во время паузы или HTTP-загрузки | Кооперативная отмена, interrupt, реакция HttpClient, join |

Код: `SnapshotCommand`, `SnapshotService`, `MarketSnapshot`.

Состояния потоков, park/unpark, UncaughtExceptionHandler и тонкости JMM показываем отдельными
демо и jcstress-опытами. Не для каждой теоретической темы придумываем отдельную функцию продукта.

## Семинар 11. Быстрее получить котировки набора инструментов и собрать результат

**Предлагаемая бизнес-задача:** пользователь запрашивает несколько инструментов; последовательные
медленные запросы слишком долго собирают всю подборку. Независимые загрузки можно выполнять
параллельно, управляя нагрузкой и сохраняя понятный результат по каждому инструменту.

**Предлагаем добавить:** запрос подборки котировок с ограниченным числом одновременно работающих
загрузок. Затем — композицию результатов в отчёт: какие инструменты загрузились, где возникла
ошибка или истёк срок ожидания. Это развитие загрузки данных; согласованный снимок из семинара 10
сохраняем как пример публикации готовой версии.

| Требование | Какую тему закрываем |
|---|---|
| Выполнить независимые загрузки параллельно | ExecutorService, задачи вместо ручного управления Thread |
| Ограничить работников и накопление запросов | ThreadPoolExecutor, размер пула, ограниченная очередь, отказ в приёме |
| Получить цену либо ошибку конкретной загрузки | Callable, submit, Future.get, ExecutionException |
| Отменить ненужные задачи и закрыть сервис | Future.cancel(true), shutdown / shutdownNow, awaitTermination |
| Преобразовать и объединить результаты без цепочки блокирующих get | CompletableFuture: thenApply, thenCompose, thenCombine / allOf, явный executor |
| Представить частичные ошибки пользователю | handle / exceptionally, политика частичного результата и таймаута |

**Подготовка:** сейчас учебная команда получает набор через `fetchQuotes()`. Для независимых
загрузок нужно определить API запроса по инструменту и добавить соответствующие mock-ответы
с разными задержками и ошибками. Не выдаём один общий HTTP-запрос за несколько независимых.

Для отчёта можно показывать частичный результат. Для публикации нового полного снимка отдельно
определяем правило: например, публиковать только после успешной загрузки всей подборки.
Таймаут CompletableFuture сам по себе не гарантирует отмену сетевой работы; отмену обсуждаем
на конкретном API, а не обещаем автоматическое прерывание всей цепочки.

## Семинар 12. Масштабировать ту же загрузку на множество ожидающих запросов

**Предлагаемая бизнес-задача:** набор инструментов или число одновременных запросов растёт.
Большая часть времени уходит на ожидание сети; хочется сохранить простой блокирующий код,
не создавая отдельный дорогой платформенный поток на каждую загрузку.

**Предлагаем изменить:** выполнить ту же подборку через executor с виртуальным потоком на задачу.
Бизнес-результат и сценарий mock-server сохраняем, чтобы сравнить модели выполнения на одной работе.

| Требование | Какую тему закрываем |
|---|---|
| Обслужить много одновременно ожидающих I/O-задач | Virtual threads, M:N, carrier threads, virtual-thread-per-task executor |
| Сохранить последовательный код отдельной загрузки | Блокирующий HttpClient в виртуальном потоке |
| Не перегрузить внешний API | Отдельный лимит одновременных обращений, например Semaphore; число virtual threads не равно разрешённой нагрузке |
| Корректно отменить подборку и закрыть исполнителя | Отмена задач, прерывание блокирующего I/O, управление жизненным циклом |
| Выбрать подход для реальной нагрузки | Сравнение платформенного пула, CompletableFuture и virtual threads; I/O-bound против CPU-bound |

Количество задач и лимит обращений варьируем отдельно. Обсуждаем, почему виртуальные потоки
не ускоряют CPU-вычисления и не увеличивают пропускную способность внешнего сервера.
Pinning и ThreadLocal разбираем отдельными примерами с учётом используемой версии JDK.

---

Линия развития проекта: **доступный и согласованный снимок → управляемая параллельная загрузка
и композиция результатов → масштабирование того же I/O-сценария виртуальными потоками**.
Для семинаров 11–12 сначала согласуем конкретные пользовательские команды и правила ошибок,
после чего детализируем реализацию. Здесь фиксируем бизнес-мотивацию и связь с темами.

### Исходный семинар 10: ускорение загрузки и прогресс

**Бизнес-задача:** команды аналитики долго ждут последовательные запросы котировок. Нужно
распараллелить загрузку набора тикеров и показывать, сколько работы уже выполнено.

- В `QuoteService.quotesFor` создаётся платформенный поток на тикер. Результат записывается
  в отдельную ячейку массива, после join собирается список с сохранением порядка тикеров.
- Вызовы прогресса подключены к командам `stats`, `movers`, `compare`; `ProgressBar` рисует
  число завершённых задач в stderr, отдельно от основного результата.
- Общий счётчик завершений — `AtomicInteger`. Это повод обсудить потерянный инкремент,
  отличие volatile от атомарности, CAS и AtomicReference.
- Потоки/ОС, прерывание, JMM, happens-before и final связываются с загрузкой и передачей результатов.
- Практика для студентов: распараллеливание, корректное ожидание и сравнение времени до/после.

**Отличие от текущего плана:** вместо этой загрузки в нашем 10-м уже реализован согласованный
фоновый снимок. Параллельную подборку переносим на 11-й; прогресс остаётся возможным дополнением.
Подробный CAS-блок исходного плана не следует считать автоматически включённым в текущий объём.

### Исходный семинар 11: повторные запросы без повторного похода в сеть

**Бизнес-задача:** несколько потоков загружают одинаковые инструменты; нужен общий кеш,
который сохраняет результаты и сокращает повторные обращения к источнику.

- Учебная линия: общий HashMap → гонки/check-then-act → грубая защита монитором → ConcurrentHashMap.
- В итоговом `QuoteService` кеш — ConcurrentHashMap, загрузка идёт через computeIfAbsent.
- `figiCache` в `HttpQuoteSource` тоже переведён на ConcurrentHashMap; там остаётся get/put,
  а не атомарная дедупликация сетевого поиска.
- Через кеш обсуждаются монитор, synchronized, wait/notify, CAS и устройство конкурентной карты.
- Отдельная практика — `SynchronizerExercisesTest`: дождаться N работников (CountDownLatch),
  ограничить одновременность запросов (Semaphore), собрать потоки (CyclicBarrier), пройти фазы
  (Phaser), прочитать значение оптимистично (StampedLock). Exchanger присутствует в теории.
- Коллекции разбираются через blocking / lock-free / wait-free; для watchlist предложен
  CopyOnWrite-вариант, для producer/consumer — BlockingQueue. Это кандидаты/иллюстрации,
  не все они внедрены в приложение.

**Отличие от текущего плана:** отдельного семинара синхронизаторов и concurrent-коллекций
сейчас нет. Кеш/дедупликация и упражнения — запас идей, а не уже запланированный большой блок
на 11-м. Ограничение одновременности естественно подходит к нашей задаче 12-го.

Источники: [план семинара 11](https://github.com/SHvatov/ab-java-seminars-2026/blob/f4819e572e5cbcd726a95f2ee6bf4a56f1d5aa0b/advanced/docs/seminars/seminar11/%D0%9F%D0%BB%D0%B0%D0%BD%20%D1%81%D0%B5%D0%BC%D0%B8%D0%BD%D0%B0%D1%80%D0%B0.md); [QuoteService](https://github.com/SHvatov/ab-java-seminars-2026/blob/f4819e572e5cbcd726a95f2ee6bf4a56f1d5aa0b/advanced/src/main/java/academy/backend/market_pulse/service/QuoteService.java); [упражнения](https://github.com/SHvatov/ab-java-seminars-2026/blob/f4819e572e5cbcd726a95f2ee6bf4a56f1d5aa0b/advanced/src/test/java/academy/backend/market_pulse/concurrent/SynchronizerExercisesTest.java).

### Исходный семинар 12: смена исполнителя и асинхронная обработка

**Бизнес-задача:** сохранить загрузку набора котировок, но убрать ручное управление Thread,
обрабатывать результаты по готовности и масштабировать ожидание сети.

- В плане сначала ручные потоки заменяются ExecutorService/Callable/Future с фиксированным пулом.
- Затем предлагается перевести загрузку на CompletableFuture: преобразование/композиция,
  выбор executor, обработка ошибки одного тикера без падения всей подборки.
- В итоговом коде ветки `quotesFor` уже использует supplyAsync с явно заданным virtual-thread-per-task
  executor и собирает результаты через join; сохраняются ConcurrentHashMap и AtomicInteger.
  Предложенный в плане этап с exceptionally не следует выдавать за реализованную защиту всех стадий:
  в этом методе её нет.
- Виртуальные потоки объясняются через carrier, continuation, mount/unmount; код отдельной
  блокирующей загрузки сохраняется при смене исполнителя.
- `VirtualThreadsBenchmark` сравнивает фиксированный пул из 8 работников с виртуальными потоками
  на 100/1000 задачах с sleep(5 ms). Исполнители создаются на trial, не в измеряемом методе.
  Это модель ожидающей нагрузки, не сетевой нагрузочный тест и не замер CPU-bound сценария.

**Отличие от текущего плана:** Executor/Future/CompletableFuture переносим на 11-й, а 12-й
оставляем виртуальным потокам и сравнению моделей на одной задаче. Идею бенчмарка можно
переиспользовать как отдельное демо, не обещая универсальный выигрыш по его результатам.

### Что полезно сохранить из первоначальной линии

| Идея | Роль в нынешнем модуле |
|---|---|
| Один и тот же quotesFor развивается несколько занятий | Сравнивать модели исполнения на одинаковой бизнес-задаче |
| Прогресс загрузки | Возможное расширение 11-го: наблюдаемый результат параллельной работы, атомарный счётчик |
| Кеш и дедупликация одинаковых тикеров | Кандидат для отдельного разбора общего состояния; требует места в программе |
| Лимит одновременных сетевых обращений | Практическая необходимость при масштабировании на 12-м |
| Смена executor без смены логики задачи | Мост между 11-м и 12-м |
| JMH на модельном ожидании | Дополнительный эксперимент 12-го с чётко обозначенными ограничениями |

Первичные реализации — референс, не готовый код для переноса без адаптации. В частности,
`joinQuietly` исходного 10-го только восстанавливает флаг, но не организует полноценную отмену
всех работников; блокирующий HTTP внутри computeIfAbsent из 11-го требует отдельного обсуждения.
Эти решения не заменяют согласованные контракты отмены и нагрузки в новом проекте.
