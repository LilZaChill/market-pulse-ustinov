## Семинар 10. Собственный исполнитель для временных подписок

Пользователь запускает `subscriptions --workers 3` и вводит:

```text
watch SBER 3s 30s
watch GAZP 5s 1m
remove SBER
exit
```

**Уже реализовано:** основной поток читает команды, один dispatcher следит за сроками,
N платформенных работников выполняют задачи из стека Трайбера. Каждый refresh обращается
к существующему HTTP-endpoint каталога и выбирает нужный тикер; отдельного per-ticker API нет.

Первый запрос готов сразу, но может ждать свободного работника. Следующий — через интервал
после ответа (fixed delay). На одну подписку приходится не более одной queued/running задачи.
После срока новая загрузка не начинается; допущенная до срока может закончиться.
Ошибка выводится, подписка продолжает работать до срока или отмены.

Remove снимает одну подписку, отменяет ожидающую работу и прерывает выполняющуюся загрузку.
Узел отменённой задачи может оставаться в стеке до извлечения, но HTTP не запускает.
Другие подписки продолжаются, тот же тикер можно зарегистрировать заново.
Exit/EOF прекращает планирование, очищает ожидающие задачи, прерывает работников и ждёт завершения.

| Бизнес-требование | Какую тему раскрываем |
|---|---|
| Сохранять ввод доступным во время сети | Thread/Runnable, разделение ролей потоков |
| Не занимать работника интервалом подписки | Отдельный dispatcher, timed wait, condition loop |
| Публиковать задачу другому потоку | Immutable Node, AtomicReference, CAS, happens-before |
| Ждать работу без busy-loop | park/unpark, permit и повторная проверка |
| Изолировать ошибку одной загрузки | Обработка исключения задачи против UncaughtExceptionHandler потока |
| Отменить одну подписку без влияния на остальные | cancelled/runner под монитором, адресный interrupt |
| Завершить сервис во время HTTP | Поддержка отмены HttpClient, shutdown, join |

Пример развивается на переходах в IDE, после JMM запускается целиком. Jcstress показываем
в коде: TreiberPushPlain/Cas — потеря push и атомарность; PublicationPlain/Volatile — видимость.
Нужные гарантии уже есть у AtomicReference; отдельный volatile не делает составной push атомарным.

Учебные ограничения: LIFO без справедливости, неограниченный стек, пробуждение всех работников,
нет Future и замены worker после Error. Стек lock-free; весь пул так не называем, поскольку
submit/shutdown согласованы монитором. Полный контракт — в [описании практики](../seminar10/Практика%20—%20подписки%20на%20котировки.md).
Команда snapshot остаётся дополнительным примером immutable-публикации, не основной практикой.

## Семинар 11. Синхронизаторы и коллекции, затем стандартные исполнители

**Бизнес-задача:** сохранить работающий сценарий подписок, но делегировать управление задачами,
расписанием и отменой стандартной библиотеке. Рефакторинг опирается на поведение из семинара 10.

Начинаем с Q&A (~10–15 минут), затем обсуждаем атомики, высокоуровневые синхронизаторы
и потокобезопасные коллекции. После этого переходим к Executor Framework и рефакторингу
исполнения и планирования. Отдельно разбираем ForkJoinPool: декомпозицию и work stealing.
Он служит примером другой модели задач; сетевые загрузки подписок не требуют автоматического
переноса на ForkJoinPool.

| Что меняем / обсуждаем | Тема |
|---|---|
| Самописный пул → ExecutorService / ThreadPoolExecutor | Задача отдельно от исполнителя, размер пула и очередь |
| Собственный dispatcher → ScheduledExecutorService | Стандартное расписание, fixed delay / fixed rate |
| Ручное отслеживание выполнения → Future / ScheduledFuture | Callable, результат, исключения, cancel |
| Учебный immediate shutdown → явная политика остановки | shutdown / shutdownNow / awaitTermination |
| Собственный CAS-стек → выбор стандартной структуры задач | BlockingQueue и неблокирующие очереди, LIFO/FIFO и справедливость |
| Разбор знакомого CAS и общего состояния | Атомики, составные операции, блокирующая и неблокирующая синхронизация |

Сохраняем watch/remove/exit, срок и отсутствие перекрытия обновлений. Fixed delay должен
отсчитываться после HTTP-ответа: окончание submit само по себе не означает окончание запроса.
При отмене учитываем и запланированное повторение, и уже выполняющийся HTTP-запрос.
Переход со стека LIFO на FIFO и со своего shutdown на стандартный обсуждаем как изменение
политики обслуживания, а не молчаливую эквивалентную замену.

Атомики и потокобезопасные коллекции — часть этого занятия. Возможное небольшое расширение:
счётчик выполненных загрузок и реестр активных подписок как повод выбрать AtomicInteger,
ConcurrentHashMap или защиту монитором. Конкретные структуры выбираем при детализации;
не добавляем их исключительно ради наличия класса в примере.

Загрузка подборки, прогресс-бар, кеш/дедупликация остаются запасными задачами из летних материалов.
Они не должны вытеснить основной рефакторинг. CompletableFuture не входит в обязательный объём 11-го.

## Семинар 12. Краткий обзор CompletableFuture, затем виртуальные потоки

В начале поверхностно знакомимся с CompletableFuture: асинхронный результат, цепочки,
композиция и ошибки. Затем разбираем анатомию виртуальных потоков, опираясь на авторскую
презентацию выступления «Виртуальные потоки» из директории с презентациями.

**Бизнес-задача:** обслуживать много подписок с блокирующими сетевыми ожиданиями,
сохраняя понятный код отдельной загрузки и управляемую нагрузку на источник.

| Требование | Тема |
|---|---|
| Много одновременно ожидающих загрузок | Virtual-thread-per-task executor, M:N и carrier threads |
| Сохранить блокирующий HTTP-код | Mount/unmount, continuation, освобождение carrier при поддерживаемом ожидании |
| Не перегрузить источник | Отдельный лимит обращений, например Semaphore, независимо от числа virtual threads |
| Сохранить remove/exit и срок | Отмена задач, прерывание I/O и завершение исполнителей |
| Обоснованно выбрать модель | Сравнение с платформенным пулом; I/O-bound и CPU-bound |

Планирование интервалов не смешиваем с исполнением HTTP. Сравниваем один сценарий с одинаковыми
правилами, а не разные задачи. Обсуждаем pinning и ThreadLocal с учётом версии JDK.
JMH на модельном ожидании можно оставить дополнительным экспериментом; он не доказывает
универсального выигрыша и не заменяет измерение реального внешнего сервиса.

## Роль CompletableFuture в практике

Краткий обзор входит в начало 12-го; переписывать весь сценарий подписок на цепочки не требуется.
Для иллюстрации можно собрать результаты нескольких загрузок с частичными ошибками.
Подробное изучение API остаётся дополнительным материалом. Таймаут или отмена стадии
не должны автоматически трактоваться как прерывание HTTP-запроса.

конкурентные структуры → масштабирование той же работы виртуальными потоками**.

### Исходный семинар 10: ускорение загрузки и прогресс

**Бизнес-задача:** команды аналитики долго ждут последовательные запросы котировок. Нужно
распараллелить загрузку набора тикеров и показывать, сколько работы уже выполнено.

- В `QuoteService.quotesFor` создаётся платформенный поток на тикер. Результат записывается
  в отдельную ячейку массива, после join собирается список с сохранением порядка тикеров.
- Вызовы прогресса подключены к командам `stats`, `movers`, `compare`; `ProgressBar` рисует
  число завершённых задач в stderr, отдельно от основного результата.
- Общий счётчик завершений — `AtomicInteger`. Это повод обсудить потерянный инкремент,
  отличие volatile от атомарности, CAS и AtomicReference.
- Потоки/ОС, прерывание, JMM, happens-before и final связываются с загрузкой и передачей результатов.
- Практика для студентов: распараллеливание, корректное ожидание и сравнение времени до/после.

**Отличие от текущего плана:** вместо этой загрузки основным примером 10-го теперь стали временные подписки через учебный пул.
Снимок остаётся дополнительным демо. Подборку и прогресс можно добавить на 11-м.
CAS уже включён в текущий 10-й на стеке Трайбера; прогресс и полный обзор Atomic* остаются отдельными вопросами 11-го.

### Исходный семинар 11: повторные запросы без повторного похода в сеть

**Бизнес-задача:** несколько потоков загружают одинаковые инструменты; нужен общий кеш,
который сохраняет результаты и сокращает повторные обращения к источнику.

- Учебная линия: общий HashMap → гонки/check-then-act → грубая защита монитором → ConcurrentHashMap.
- В итоговом `QuoteService` кеш — ConcurrentHashMap, загрузка идёт через computeIfAbsent.
- `figiCache` в `HttpQuoteSource` тоже переведён на ConcurrentHashMap; там остаётся get/put,
  а не атомарная дедупликация сетевого поиска.
- Через кеш обсуждаются монитор, synchronized, wait/notify, CAS и устройство конкурентной карты.
- Отдельная практика — `SynchronizerExercisesTest`: дождаться N работников (CountDownLatch),
  ограничить одновременность запросов (Semaphore), собрать потоки (CyclicBarrier), пройти фазы
  (Phaser), прочитать значение оптимистично (StampedLock). Exchanger присутствует в теории.
- Коллекции разбираются через blocking / lock-free / wait-free; для watchlist предложен
  CopyOnWrite-вариант, для producer/consumer — BlockingQueue. Это кандидаты/иллюстрации,
  не все они внедрены в приложение.

**Отличие от текущего плана:** атомики и конкурентные коллекции теперь входят в 11-й вместе
с рефакторингом исполнителя. Полный обзор всех синхронизаторов и кеш/дедупликация не становятся
обязательной практикой автоматически. Ограничение внешних обращений пригодится на 12-м.

Источники: [план семинара 11](https://github.com/SHvatov/ab-java-seminars-2026/blob/f4819e572e5cbcd726a95f2ee6bf4a56f1d5aa0b/advanced/docs/seminars/seminar11/%D0%9F%D0%BB%D0%B0%D0%BD%20%D1%81%D0%B5%D0%BC%D0%B8%D0%BD%D0%B0%D1%80%D0%B0.md); [QuoteService](https://github.com/SHvatov/ab-java-seminars-2026/blob/f4819e572e5cbcd726a95f2ee6bf4a56f1d5aa0b/advanced/src/main/java/academy/backend/market_pulse/service/QuoteService.java); [упражнения](https://github.com/SHvatov/ab-java-seminars-2026/blob/f4819e572e5cbcd726a95f2ee6bf4a56f1d5aa0b/advanced/src/test/java/academy/backend/market_pulse/concurrent/SynchronizerExercisesTest.java).

### Исходный семинар 12: смена исполнителя и асинхронная обработка

**Бизнес-задача:** сохранить загрузку набора котировок, но убрать ручное управление Thread,
обрабатывать результаты по готовности и масштабировать ожидание сети.

- В плане сначала ручные потоки заменяются ExecutorService/Callable/Future с фиксированным пулом.
- Затем предлагается перевести загрузку на CompletableFuture: преобразование/композиция,
  выбор executor, обработка ошибки одного тикера без падения всей подборки.
- В итоговом коде ветки `quotesFor` уже использует supplyAsync с явно заданным virtual-thread-per-task
  executor и собирает результаты через join; сохраняются ConcurrentHashMap и AtomicInteger.
  Предложенный в плане этап с exceptionally не следует выдавать за реализованную защиту всех стадий:
  в этом методе её нет.
- Виртуальные потоки объясняются через carrier, continuation, mount/unmount; код отдельной
  блокирующей загрузки сохраняется при смене исполнителя.
- `VirtualThreadsBenchmark` сравнивает фиксированный пул из 8 работников с виртуальными потоками
  на 100/1000 задачах с sleep(5 ms). Исполнители создаются на trial, не в измеряемом методе.
  Это модель ожидающей нагрузки, не сетевой нагрузочный тест и не замер CPU-bound сценария.

**Отличие от текущего плана:** Executor/Future переносим на 11-й; виртуальные потоки — фокус 12-го.
CompletableFuture поверхностно разбираем в начале 12-го, затем переходим к анатомии виртуальных потоков. Идею бенчмарка можно
переиспользовать как отдельное демо, не обещая универсальный выигрыш по его результатам.

### Что полезно сохранить из первоначальной линии

| Идея | Роль в нынешнем модуле |
|---|---|
| Один и тот же quotesFor развивается несколько занятий | Сравнивать модели исполнения на одинаковой бизнес-задаче |
| Прогресс загрузки | Возможное расширение 11-го: наблюдаемый результат параллельной работы, атомарный счётчик |
| Кеш и дедупликация одинаковых тикеров | Кандидат для отдельного разбора общего состояния; требует места в программе |
| Лимит одновременных сетевых обращений | Практическая необходимость при масштабировании на 12-м |
| Смена executor без смены логики задачи | Мост между 11-м и 12-м |
| JMH на модельном ожидании | Дополнительный эксперимент 12-го с чётко обозначенными ограничениями |

Первичные реализации — референс, не готовый код для переноса без адаптации. В частности,
`joinQuietly` исходного 10-го только восстанавливает флаг, но не организует полноценную отмену
всех работников; блокирующий HTTP внутри computeIfAbsent из 11-го требует отдельного обсуждения.
Эти решения не заменяют согласованные контракты отмены и нагрузки в новом проекте.
